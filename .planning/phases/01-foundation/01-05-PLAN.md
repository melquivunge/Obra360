<threat_model>
## STRIDE Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | role assignment | mitigate | StoreUserRequest validates role via Rule::in(four constants); UserPolicy + role:admin restrict all actions to admins |
| T-05-02 | Tampering | Mass assignment | mitigate | Form requests pass only validated() data; User Fillable whitelist; active set server-side |
| T-05-03 | Information Disclosure | Password handling | mitigate | Password stored via 'hashed' cast; never echoed back in edit form |
| T-05-04 | Repudiation | User deletion | mitigate | Soft delete (deleted_at) keeps the record; JS confirm prevents accidental deletes (USR-04, SEC-06) |
| T-05-05 | Tampering | State-changing GETs | mitigate | toggle-active and destroy use POST/DELETE forms with @csrf, never GET links |

**Assets:** User accounts, role assignments, credentials.
**Attack vectors:** Privilege escalation via crafted role values, mass assignment, CSRF on state changes, accidental/ malicious deletion.
**Mitigations:** role whitelist validation, admin-only policy + middleware, validated()-only persistence, CSRF-protected POST/DELETE actions, soft delete + confirm dialog.
**Residual risks (verify manually):** Confirm a manager/financial/client cannot reach any /usuarios route (covered by UserManagementTest 403 assertion) and that the edit form never pre-fills the password value.
</threat_model>
